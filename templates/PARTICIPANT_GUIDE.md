# 참가자 가이드 (본선 당일, r4-3.18b)

이 파일은 참가자가 보는 안내서다. 에이전트는 과제를 처음 보고할 때 이 파일 경로를 알려 준다.
설치 위치: `<과제 폴더>\.hackathon-kit\run\PARTICIPANT_GUIDE.md` (원본: `.hackathon-kit\templates\PARTICIPANT_GUIDE.md`)
아래 「」 안의 문장은 에이전트 대화창에 그대로 붙여 넣는다.

## 0. 세 줄 요약
- 에이전트가 맨 앞에 `[참가자 확인]`을 붙여 묻는 세 번은 꼭 답한다. 나머지 시간은 지켜보며 아래 증상표만 본다.
- 무효·0점·반려 규칙은 점수보다 먼저다. 숨은 평가는 공개 자료보다 거칠기 때문에 한도에 딱 붙은 안은 내지 않는다.
- 단순한 기준안보다 나쁜 안은 내지 않는다. 점심 전에 낼 수 있는 안을 하나 만들어 두고, 오후에 더 좋게 만든다.

## 1. 하루 흐름 (시작 시각 기준)
| 시점 | 에이전트가 하는 일 | 참가자가 할 일 |
|---|---|---|
| 시작 ~ 15분 | 키트 설치, doctor, 과제 문서 읽기 | doctor 값이 미리 받은 값과 같은지 본다 |
| ~ 1시간 | CP1: 규칙 표(HARD_RULES), 담당자 질문 목록, 단순 기준안·탐색 계획 | **[참가자 확인 1]** 표를 보고 답한다 (2장 A) |
| 점심 전 | 첫 제출 가능안 완성 (한도 여유 안쪽, 기준안 이상) | 「지금 낼 수 있는 안이 있는지 한 줄로 알려 줘.」 |
| 오후 | 개선 라운드 (튜닝 기간 점수로만 고르기) | 같은 오류가 오래 남으면 **[참가자 확인 2]** (2장 B) |
| 잠금 60~30분 전 | final 검사, 기준안 비교, 한도 여유 확인 | **[참가자 확인 3]** (2장 C) |
| 잠금 | 제출물 고정 | 새 아이디어를 넣지 않는다 |
| 잠금 뒤 | 학습 자료, 후속 질문 대비 | 「제출안 설명을 세 줄로, 예상 질문 다섯 개와 답을 정리해.」 |

작업 잠금 시각과 제출 방법은 과제 안내를 따른다.

## 2. 시점별로 보낼 문장
**A. CP1 표를 받았을 때 ([참가자 확인 1])**
- 문제 없으면: 「표 그대로 진행해.」
- 후보 뜻이 하나뿐인 규칙이 있으면: 「이 규칙에 다른 뜻은 없는지 원문 줄을 다시 찾아 봐. 두 뜻이 가능하면 두 뜻을 모두 지키는 쪽으로 해.」
- 숫자 한도가 있으면: 「무효·0점·반려 한도마다 여유값을 표에 적어. 자체 시험 값은 공개 재현과 스트레스 모두 그 여유 안쪽이어야 해.」
- 담당자 질문: 「두 뜻이 갈리는 규칙부터 담당자에게 물어봐. 답을 유도하지 말고 뜻만 물어.」

**B. 같은 오류가 30분 넘게 남을 때 ([참가자 확인 2])**
- 「가) 이유를 기록하고 넘어가서 제출물부터 완성해.」

**C. 잠금 30분 전 ([참가자 확인 3])**
- 「한도까지 여유가 큰 안으로 내. 제출안이 단순 기준안보다 나쁘면 기준안을 내.」

**D. 언제든 상황이 궁금할 때**
- 「지금 상태를 다섯 줄로: 낼 수 있는 안이 있는지, 한도까지 남은 여유, 기준안 대비 점수, 남은 일, 남은 시간.」

**E. 시간이 모자랄 때**
- 「새 기능은 멈추고, 지금 안으로 final 검사부터 돌려.」

**F. 점수가 너무 좋게 나올 때**
- 「평가 기간 자료가 튜닝에 섞이지 않았는지, 튜닝에 쓰지 않은 기간으로 다시 확인해.」

## 3. 증상별 대응
| 화면에 보이는 것 | 뜻 | 보낼 문장 |
|---|---|---|
| 같은 FAIL 문장이 30분 넘게, 또는 세 번 고친 뒤에도 남음 | 고치는 데 시간이 너무 듦 | 2장 B |
| `breaks the limit` | 자체 시험에서 한도를 넘음 | 「그 안은 버리고 한도 안쪽 안으로 되돌려.」 |
| `not inside the CP1 margin` | 한도는 지켰지만 여유가 모자람 | 「여유 안쪽이 될 때까지 더 보수적인 설정으로 바꿔.」 |
| `worse than` 기준안 / baseline_guard FAIL | 제출안이 단순안보다 나쁨 | 「기준안을 제출안으로 하고, 남은 시간에만 개선해.」 |
| `has not run planned stress` | 계획한 스트레스 시험을 안 함 | 「계획한 스트레스 시험을 모두 돌리고 값을 적어.」 |
| 에이전트가 표·질문 없이 바로 구현을 시작함 | CP1 확인을 건너뜀 | 「구현 멈추고 HARD_RULES 요약 표부터 보여 줘.」 |
| 5분 넘게 진행 표시만 돌고 출력이 없음 | 앱이 멈춤 | 6장 |
| 사용량 한도 안내가 뜸 | 계정 사용량 소진 | 진행자·계정을 확인한다. 작업 파일은 과제 폴더에 남아 있다 |

## 4. "한도"가 뭔가
- 과제 문서에 "~을 넘으면 무효 / 0점 / 불합격 / 반려"처럼 숫자로 적힌 선이 한도다. 한 번이라도 넘으면 그 제출물의 점수 전체를 잃는다.
- 감점(PENALTY)은 넘은 만큼 깎이고, 목표(TARGET)는 모자라도 넘쳐도 손해다. 둘은 한도와 다르게 다룬다.
- 숨은 평가는 공개 자료보다 거칠다. 그래서 CP1에서 한도마다 여유값을 정한다(권장: 한도의 10%, 건수 한도면 1건 이상). 자체 시험 값이 여유 안쪽이 아니면 키트가 FAIL을 낸다.
- 한도는 과제마다 다르고, 에이전트가 과제 문서에서 찾아 표에 적는다. 참가자가 미리 알 필요는 없다.
- 숫자 한도가 없는 과제면 표에 "숫자 기준 없음"과 그 이유가 적힌다. 그때는 단순 기준안을 이기는지와 평가 방식이 핵심이다.

## 5. 평가 방법이 흐린 과제
- 「과제를 세 줄로 다시 말해 봐: 무엇을 만드는지, 누가 어떻게 평가하는지, 제출물이 무엇인지.」
- 「평가 방법을 담당자에게 먼저 물어봐.」
- 「비교할 단순안 하나와 잴 숫자 하나를 정해.」
- 「범위를 좁혀서 한 가지를 확실히 끝내.」

## 6. 앱이 멈췄을 때
1. 앱 메뉴에서 앱을 완전히 종료한다.
2. 앱을 다시 실행하고, 대화를 다시 시작하는 버튼이 보이면 누른다.
3. 작업 파일은 과제 폴더에 남아 있다. 첫 문장: 「run/FINALS_RUN.md와 SPEC_DRAFT를 먼저 다시 읽고 하던 일을 이어서 해.」

## 7. 하지 말 것
- 검사 결과 파일을 손으로 고치게 하지 않는다. 명령을 다시 실행하게 한다.
- 잠금 직전에 새 아이디어를 넣지 않는다.
- 평가 기간 자료로 튜닝하지 않는다.
- 권한 요청 창에서는 "이번 한 번만 허용"을 쓰고 "항상 허용"은 누르지 않는다.
- 담당자에게 정답을 유도하는 질문을 하지 않는다. 뜻만 묻는다.
